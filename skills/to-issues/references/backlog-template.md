# Backlog template

Scaffold for a fresh tracker. Create **both** files — `issues/BACKLOG.md` and `issues/ARCHIVE.md` — from the blocks below, replacing `<project>` and the doc links with the project's real paths.

**Both Order tables start empty.** Do not copy an example row: a placeholder row is a `todo` entry pointing at an issue file that does not exist, and the orchestrator will dispatch a worker straight at it. Append the first real row when you write the first real issue.

Do not add columns. Five is the whole schema — anything richer belongs in the issue file.

---

## `issues/BACKLOG.md`

```md
# <project> backlog

Live delivery queue for AI agents. Completed issues move to [`ARCHIVE.md`](./ARCHIVE.md).
Source spec: [`INTENT-AND-DESIGN.md`](../docs/INTENT-AND-DESIGN.md) if present, else [`REQUIREMENTS-AND-NOTES.md`](../docs/REQUIREMENTS-AND-NOTES.md). Domain glossary: [`CONTEXT.md`](../CONTEXT.md).

## Order

| #   | Issue | Type | Blocked by | Status |
|-----|-------|------|------------|--------|

## Status values

| Status        | Meaning                                                  |
|---------------|----------------------------------------------------------|
| `todo`        | Not started; blockers (if any) are `done`                |
| `in progress` | Active worker or orchestration session                   |

Accepted issues are not listed here — their rows live in [`ARCHIVE.md`](./ARCHIVE.md) with status `done`.

## For agents

**If you were dispatched at a specific issue:** do not edit this file at all — whoever dispatched you owns `Status`. Work only that issue, mark its acceptance criteria `[x]` as you complete them, and report everything else back.

**If you are picking work yourself:** take the lowest `#` where `Status` is `todo` and every `Blocked by` issue appears in [`ARCHIVE.md`](./ARCHIVE.md) as `done`. Set `Status` → `in progress` when you start, and move the row to the archive with `Status` → `done` when it is finished and verified.

Either way: criteria tagged `proof: runtime` or `proof: migration` need observed evidence — run the thing and record what happened — not a passing unit test. Implement test-first: one failing test → minimal code to pass → repeat, with tests asserting on public behaviour rather than internals.

Do not add a second tracker. This file plus `ARCHIVE.md` and the issue files are the whole system.
```

## `issues/ARCHIVE.md`

```md
# <project> backlog archive

Accepted issues, most recent last. Rows move here from [`BACKLOG.md`](./BACKLOG.md) when the acceptance gate passes.
Issue numbers are never reused — when picking the next id, check the highest `#` here as well as in `BACKLOG.md`.

| #   | Issue | Type | Blocked by | Status |
|-----|-------|------|------------|--------|
```

## Notes

**Never link a skills install path.** A tracker that says `.agents/skills/tdd/` breaks under any harness that installs to `.claude/skills/` or elsewhere.

**Do not name bundle skills in the generated files either.** These files land in someone else's repo and outlive any particular install — a tracker instructing future agents to "use the `tdd` skill" is broken for anyone who installed only part of the bundle. State the *rule* inline instead, as the "For agents" section above does.

**Dependency notes** go below the Order table as prose when a chain matters:

```md
**Store migration (023 → 024 → 026):** schema → verification → stats parity.
```
